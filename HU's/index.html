Lazy promt¶

actúa como un ingeniero de prompt, se quiere desarrolllar un proyecto de clase para el curso de Deep learning de la Universidad NAcional de Colombia, tu tarea es crear un flujo de trabajo completo que permita el desarrollo del mismo, el proyecto es crear un modelo de redes neuronales para pronósticar el precio de bolsa de energía de colombia (el dataset se encuentra en el portal SIMEM), es importarte que tengas en cuenta el ciclo de vida de la análitica que es algo así: obtención de datos, transformación, modelado, resultados, presentación. ten en cuenta metodología DevOps, Scrum u otra que consideres apropiada, también ten presente que se cuenta con un repositorio Github que posee la siguiente estructura de carpetas

├── config/              # Parámetros del proyecto (rutas, hiperparámetros, credenciales de ejemplo).
├── data/
│   ├── raw/             # Datos originales e inmutables.
│   ├── interim/         # Datos en transformación, resultados parciales de limpieza.
│   ├── processed/       # Datos limpios y listos para modelado.
│   └── external/        # Datos de terceros o fuentes externas.
├── docs/                # Documentación del proyecto (Sphinx/MkDocs), guías y referencias.
├── models/              # Modelos entrenados y serializados (ej. .pkl, .h5).
│   ├── trained/         # Modelos finales listos para inferencia.
│   ├── checkpoints/     # Puntos de guardado durante entrenamiento.
├── notebooks/           # Jupyter Notebooks para exploración y visualización (nombrados secuencialmente).
├── src/                 # Código fuente principal del proyecto.
│   ├── __init__.py
│   ├── data/            # Scripts para ingesta y transformación de datos.
│   ├── utils/           # Funciones utilitarias y helpers.
│   ├── features/        # Scripts de feature engineering.
│   ├── models/          # Scripts para entrenamiento, optimización y predicción.
│   └── visualization/   # Generación de gráficos y pósteres digitales.
├── tests/               # Pruebas unitarias y de integración.
├── dashboards/          # Aplicaciones interactivas.
├── reports/             # Resultados y comunicación.
│   ├── figures/         # imágenes generadas por scripts/notebooks (versionadas o regenerables).
├── scripts/             # Automatización.
├── .gitignore           # Archivos ignorados por Git.
├── environment.yml      # Dependencias para Conda.
├── requirements.txt     # Dependencias para pip.
└── README.md            # Este archivo.

prompt Gemini¶

El siguiente flujo de trabajo integra el ciclo de vida de la analítica de datos, principios de MLOps/DevOps y una gestión ágil basada en Scrum adaptada a un proyecto académico de posgrado de la Universidad Nacional de Colombia.

Para construir el proyecto de manera modular, trazable y sin deuda técnica, utiliza esta secuencia de Prompt Chaining (encadenamiento de prompts). Cada fase está diseñada para ejecutar un Sprint específico sobre tu estructura de repositorio.

Marco Metodológico del Flujo (CRISP-DM + Scrum + MLOps)¶

  • Gestión Ágil (Scrum): El desarrollo se divide en 5 Sprints alineados con las etapas analíticas. Cada prompt actúa como el Sprint Backlog técnico.
  • Ingeniería y DevOps: Se prioriza el código modular en src/ sobre los notebooks monolíticos, pruebas automatizadas en tests/, configuración centralizada en config/ y documentación continua con MkDocs.

Fase 0: Configuración de Infraestructura y DevOps (Sprint 0)¶

Objetivo: Establecer las bases del repositorio, entornos reproducibles, calidad de código y automatización inicial.

Prompt 0 (Copiar y ejecutar): "Actúa como un Ingeniero de MLOps y Arquitecto de Software Senior en Python. Estamos iniciando un proyecto de Deep Learning para la Universidad Nacional de Colombia cuyo objetivo es pronosticar el precio de bolsa de energía en Colombia utilizando datos del portal SIMEM. Basándote estrictamente en nuestra estructura de repositorio (config/, src/, tests/, docs/, scripts/, etc.), genera los archivos base para garantizar reproducibilidad y calidad de código bajo prácticas DevOps:

  1. config/config.yaml: Archivo maestro con rutas relativas a data/, parámetros de conexión a la API/portal SIMEM, ventanas temporales, semillas aleatorias (seed: 42) y parámetros base de entrenamiento.
  2. requirements.txt y environment.yml: Dependencias exactas enfocadas en series de tiempo y Deep Learning (PyTorch o TensorFlow/Keras, pandas, polars, scikit-learn, optuna, pyyaml, pytest, ruff, mkdocs-material, streamlit).
  3. .github/workflows/ci.yml: Pipeline de GitHub Actions que ejecute ruff (linter/formatter) y pytest en cada push o pull request a main.
  4. scripts/setup_env.sh: Script de automatización para inicializar el entorno y verificar la estructura de carpetas.

Asegúrate de que todo el código siga estándares PEP 8, tipado estático (typing) y principios de código limpio."

Fase 1: Obtención y Exploración de Datos (Sprint 1)¶

Objetivo: Construir el pipeline de extracción reproducible desde SIMEM hacia data/raw/ y realizar el Análisis Exploratorio de Datos (EDA) específico del mercado eléctrico colombiano.

Prompt 1 (Copiar y ejecutar): "Actúa como un Ingeniero de Datos especializado en el Mercado de Energía Mayorista (MEM) de Colombia. Vamos a desarrollar el Sprint 1: Obtención y Exploración de Datos dentro de nuestra estructura de proyecto. Considerando el dominio del problema (estacionalidad horaria/diaria, fenómenos macroclimáticos como El Niño/La Niña, aportes hídricos, demanda nacional y generación térmica/hidráulica):

  1. src/data/make_dataset.py: Escribe un script modular que descargue o cargue los datos históricos del precio de bolsa nacional y variables exógenas clave desde el portal SIMEM (usando su API pública o lectura estructurada), guardando los archivos inmutables con control de versiones por fecha en data/raw/. Incluye manejo de excepciones, logging estructurado y lectura de parámetros desde config/config.yaml.
  2. notebooks/01_eda_simem_precio_bolsa.ipynb: Diseña la estructura detallada (celdas de código y markdown) de un notebook exploratorio que analice: valores faltantes, valores atípicos (picos de escasez), estacionariedad (pruebas ADF/KPSS), autocorrelación (ACF/PACF) y descomposición estacional del precio de bolsa. Las figuras clave deben exportarse automáticamente a reports/figures/.
  3. tests/test_data_ingestion.py: Crea pruebas unitarias con pytest para validar el esquema de datos, tipos de columnas y ausencia de duplicados temporales tras la ingesta."

Fase 2: Transformación e Ingeniería de Características (Sprint 2)¶

Objetivo: Limpiar los datos, evitar fuga de información (data leakage) y construir tensores secuenciales listos para redes neuronales.

Opción 1

Prompt 2 (Copiar y ejecutar): "Actúa como un Científico de Datos Senior experto en Series de Tiempo. Ejecutemos el Sprint 2: Transformación y Feature Engineering. Utilizando los datos crudos en data/raw/ y siguiendo las reglas definidas en config/config.yaml:

  1. src/data/preprocess.py: Implementa la limpieza de datos, imputación causal (sin mirar al futuro) y alineación temporal horaria/diaria, guardando el resultado intermedio en data/interim/.

  2. src/features/build_features.py: Crea un pipeline de ingeniería de características que genere:

  3. Rezagos (lags) autorregresivos óptimos y ventanas móviles (media, desviación estándar, cuantiles).

  4. Codificación cíclica de variables temporales (\(\sin/\cos\) para hora del día, día de la semana y mes).
  5. Indicadores de dominio energético (ej. brecha demanda-aportes hídricos si están disponibles).
  6. Escalado (RobustScaler o StandardScaler) ajustado estrictamente sobre el conjunto de entrenamiento (serializando el escalador en models/trained/scaler.pkl para inferencia futura).

  7. Generación de ventanas deslizantes 3D (muestras, pasos_tiempo, características) almacenadas en data/processed/.

  8. tests/test_features.py: Implementa pruebas unitarias que garanticen que no existe data leakage entre los conjuntos de train, validation y test (split cronológico estricto)."

Opción 2

Actúa como un Científico de Datos Senior especializado en series de tiempo y en modelado de sistemas energéticos. Necesito que implementes el Sprint 2: Transformación y Feature Engineering de este proyecto, siguiendo estrictamente las reglas definidas en config/config.yaml. El objetivo es dejar listos, de forma reproducible y libre de fuga de información, los datos transformados para entrenar modelos de pronóstico.

Los datos crudos están en data/raw/. Trabaja sobre ellos respetando el orden cronológico en todo momento, porque cualquier transformación que use información futura invalidaría el pronóstico.

Implementa lo siguiente:

  1. src/data/preprocess.py: limpieza de datos, imputación causal (cada valor faltante se rellena únicamente con información disponible en el pasado, nunca con valores posteriores) y alineación temporal a frecuencia horaria y diaria. Guarda el resultado intermedio en data/interim/.

  2. src/features/build_features.py: un pipeline de ingeniería de características que genere:

  3. Rezagos (lags) autorregresivos y ventanas móviles (media, desviación estándar y cuantiles). Selecciona los rezagos a partir de evidencia del propio dato (por ejemplo, autocorrelación o autocorrelación parcial) y justifica la elección en comentarios del código.

  4. Codificación cíclica de variables temporales mediante seno y coseno para hora del día, día de la semana y mes.
  5. Indicadores de dominio energético, como la brecha entre demanda y aportes hídricos, siempre que las columnas correspondientes existan en los datos.
  6. Escalado con RobustScaler o StandardScaler, ajustado únicamente sobre el conjunto de entrenamiento. Serializa el escalador en models/trained/scaler.pkl para la inferencia futura.

  7. Generación de ventanas deslizantes tridimensionales con forma (muestras, pasos_tiempo, características), almacenadas en data/processed/.

  8. tests/test_features.py: pruebas unitarias que verifiquen la ausencia de data leakage entre los conjuntos de entrenamiento, validación y prueba. El particionado debe ser cronológico estricto. Incluye pruebas que confirmen que el escalador no fue ajustado con datos de validación ni de prueba, que la imputación no usa valores futuros y que las ventanas deslizantes no cruzan las fronteras entre particiones.

Restricciones de implementación: usa Python con las bibliotecas estándar del ecosistema científico (pandas, numpy, scikit-learn, pytest). Mantén el código modular, con funciones pequeñas y documentadas. Si alguna columna mencionada en config/config.yaml no existe en data/raw/, no la inventes: registra la omisión de forma explícita y continúa con las demás. Antes de dar por terminado el trabajo, ejecuta las pruebas y confirma que pasan.

Objetivo: Diseñar, entrenar, regularizar y optimizar arquitecturas neuronales para pronóstico de series de tiempo.

Opción 1

LSTM/GRU con mecanismo de atención, TCN - Temporal Convolutional Networks, o N-BEATS/TFT):

  1. src/models/architectures.py: Define al menos dos arquitecturas de redes neuronales en PyTorch (o TensorFlow/Keras) bien estructuradas, incluyendo capas de Dropout, normalización y funciones de pérdida robustas ante picos de precio (ej. Huber Loss o Quantile Loss para intervalos de predicción).
  2. src/models/train_model.py: Script de entrenamiento configurado desde config/config.yaml que incluya: Early Stopping, programación de tasa de aprendizaje (Learning Rate Scheduler), guardado de los mejores pesos en models/checkpoints/, y registro de métricas de entrenamiento/validación.
  3. src/models/optimize.py: Implementa una búsqueda de hiperparámetros con Optuna (tasa de aprendizaje, tamaño de ventana, unidades ocultas, dropout) que guarde los mejores parámetros y exporte el modelo campeón final a models/trained/."

Recomendaciones de Ejecución en tu Flujo de Trabajo¶

  • Iteración incremental: No ejecutes todos los prompts a la vez. Ejecuta el Prompt 0, valida que los archivos funcionen en tu entorno local y haz el primer git commit. Avanza al siguiente Sprint solo cuando los tests/ del Sprint actual pasen en verde.
  • Control de contexto: Cuando pases del Prompt \(N\) al Prompt \(N+1\), adjunta únicamente los nombres de columnas reales obtenidas de SIMEM y la arquitectura seleccionada para mantener coherencia estricta entre scripts.
  • Automatización final: Al terminar el Sprint 3, pide generar un archivo scripts/run_pipeline.sh (o Makefile) que encadene make_dataset.py \(\rightarrow\) preprocess.py \(\rightarrow\) build_features.py \(\rightarrow\) train_model.py \(\rightarrow\) predict_model.py en un solo comando.
